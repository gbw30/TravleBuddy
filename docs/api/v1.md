# HTTP API, version 1

Status: architecture
Authority: The documented routes the website uses for every change to data (TB-SYS-04), and the ones a phone app would use
Related: [Service borders](../architecture/service-borders.md), [ADR-008](../architecture/adr-008-modular-services-in-one-deployment.md), [requirements](../requirements.md)
Last reviewed: 2026-11-18

Every route is under `/api/v1`, needs a signed-in session, and answers JSON. The request and answer shapes are the Zod schemas and types in `src/features/trips/contracts.ts` and `src/features/places/contracts.ts`; this page names them and does not repeat them.

The older routes under `/api/trips` belong to the earlier planner and go when Milestones 4 to 6 replace it.

## Rules for every change to a trip

A change to an existing trip carries two fields with its body:

| Field              | Meaning                                                                         |
| ------------------ | ------------------------------------------------------------------------------- |
| `operationId`      | A UUID made by the client for this one action. Send the same one when retrying. |
| `expectedRevision` | The trip's `revision` as the client last saw it.                                |

- **Repeat:** the same `operationId` with the same body returns the first answer and changes nothing more.
- **Reuse:** the same `operationId` with a different body answers `409 operation_id_conflict`.
- **Stale:** an `expectedRevision` older than the trip answers `409 stale_revision` and changes nothing. Load the trip again and retry.
- A successful change answers `{ "data": ..., "revision": n }`, where `revision` is the trip's new revision.
- Each change commits completely or not at all.

## Errors

Every error answers `{ "error": "<code>" }`. `invalid_request` also carries `issues`.

| Status | Code                    | When                                                                                                              |
| ------ | ----------------------- | ----------------------------------------------------------------------------------------------------------------- |
| 401    | `unauthorized`          | Not signed in.                                                                                                    |
| 404    | `not_found`             | The trip or commitment does not exist or is not the caller's.                                                     |
| 409    | `stale_revision`        | The trip changed since `expectedRevision`.                                                                        |
| 409    | `operation_id_conflict` | The operation id was used for a different request.                                                                |
| 409    | `archived`              | The trip is archived. Restore it first.                                                                           |
| 409    | `cities_in_use`         | A city cannot be removed while the earlier planner's places point at it.                                          |
| 409    | `refused`               | The plan's rules do not allow the action, such as a move onto a booked item. `message` says why. Nothing changes. |
| 422    | `invalid_request`       | The body does not match the schema.                                                                               |
| 422    | `too_many`              | The trip already holds 100 commitments.                                                                           |
| 503    | `lookup_unavailable`    | City lookup could not be reached. Nothing else is affected.                                                       |
| 500    | `server_error`          | Anything unexpected. No detail is returned.                                                                       |

Another traveller's trip always answers 404, never 403, so its existence is not revealed.

Trip actions for `PATCH /api/v1/trips/{tripId}`:

| `action`  | Extra fields                | Effect                                                                              |
| --------- | --------------------------- | ----------------------------------------------------------------------------------- |
| `rename`  | `title`                     | Changes the title.                                                                  |
| `facts`   | `facts` (`tripFactsSchema`) | Saves the facts it names and leaves the rest unchanged.                             |
| `archive` | none                        | Hides the trip from Home. An archived trip refuses changes.                         |
| `restore` | none                        | Returns an archived trip to planning.                                               |
| `finish`  | none                        | Marks the plan finished: the trip becomes upcoming.                                 |
| `reopen`  | none                        | Returns a finished plan to planning.                                                |
| `mode`    | `planningMode`              | Changes the way the trip is planned: `GUIDED` or `QUICK`. Everything entered stays. |

Plan actions for `POST /api/v1/trips/{tripId}/plan` (`planActionSchema` in `src/features/itinerary/contracts.ts`):

| `type`     | Fields                                  | Effect                                                                                                                                           |
| ---------- | --------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| `pick`     | `slotId`, `placeId`                     | Puts a saved place in a slot. A place it replaces goes to the shelf.                                                                             |
| `save`     | `placeId`                               | Saves a place to the shelf.                                                                                                                      |
| `unshelve` | `placeId`                               | Takes a place off the shelf.                                                                                                                     |
| `move`     | `fromSlotId`, `toSlotId`                | Moves a place, trading with one already there. A move that breaks a rule is saved with a flag; a move onto something already decided is refused. |
| `remove`   | `slotId`                                | Removes a place from the plan.                                                                                                                   |
| `minutes`  | `slotId`, `minutes` or null             | Sets the visit length, or returns to the standard one.                                                                                           |
| `pace`     | `pace`                                  | Sets relaxed, balanced or packed.                                                                                                                |
| `transfer` | `day`, `start`                          | Moves an assumed transfer between cities.                                                                                                        |
| `undo`     | none                                    | Returns to the plan before the last change.                                                                                                      |
| `others`   | `slotId`, `placeIds`, `reasons`, `note` | "Show me others": turns down a whole set or one card, with reasons from the common list. Those places are not offered again in this trip.        |

The body may also name `focus`, the slot to show cards for afterwards; without it the next slot to fill is used. `GET` takes it as `?slot=`.

The plan in an answer holds `view` (the laid-out days), `chosen` (a card for every place in the plan and on the shelf), `proposal` (up to three cards for the slot in focus, with `short` when fewer than three fit and `status` saying whether places could be gathered) and `canUndo`. Reading a plan can make one request to the place provider, and records the cards it shows. It also holds `holding`, which is `"food"` when the slot in focus is a meal and guided planning is still waiting for the food answer (there is then no proposal), and `shelfOffer`, a shelved place that fits the open slot in focus; send `pick` with its `slotId` and `placeId` to place it. In guided planning a proposal is added to the trip's conversation the first time its cards are shown. A card carries `unconfirmed` when the place's listing cannot confirm one of the traveller's hard limits (a dietary rule or an allergy); the same mark is at the end of `essentials`. A place whose listing conflicts with a dietary rule is never in a proposal.

### A turn of the conversation

| `type`                                        | Fields                             | Effect                                                                                                                                                                                                  |
| --------------------------------------------- | ---------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `answer`                                      | `topic`, `values`                  | A tapped choice, or several, for the question that is waiting. Only that question's own choices are accepted.                                                                                           |
| `skip`                                        | `topic`                            | Skips the waiting question. The agent uses a default and says which.                                                                                                                                    |
| `answer` or `skip` with `topic: "difference"` | `values`: a purpose, or `ordinary` | Answers "is this trip different from your usual?", asked once when an answer goes against the personal profile. A typed `say` is taken as the traveller's own reason.                                   |
| `say`                                         | `text` (600 characters at most)    | A typed message. The AI model reads it into structured data when it is available; otherwise simple rules do.                                                                                            |
| `remember`                                    | none                               | Yes to the agent's offer to remember something for every trip. The offer is the last message of the thread, of kind `offer`; it goes into the personal profile. `409 refused` when no offer is waiting. |

A turn makes at most one change (trip facts, a taste answer, a fixed commitment) through the same checks as the forms, and saves what was said in the same transaction. `409 refused` means the turn named a question that is no longer waiting, or a value that is not one of its choices. `changed` in the answer says whether the turn changed the trip, its taste or its plan; a message that could not be read changes nothing. `focus` in the answer is the slot to show next when the traveller named a day ("let's do day 4"); pass it to the plan route as `?slot=`.

The waiting question in `conversation.waiting` is worked out from the trip each time it is read. Where the traveller's personal profile already holds an answer, the question asks to confirm it and carries `remembered`, the values to send back for "yes, same again". It joins the saved thread the first time the traveller responds to it.

`conversation.limited` is true when the AI model is switched off, has no key, or has reached its monthly cap. Tap choices and simple typed answers still work.

### The personal profile

The profile belongs to the signed-in traveller. No route takes a traveller's id, and another traveller's entry or note answers 404.

An entry is one value on a topic, with how sure the site is (`think`, `usually`, `always`) and where it came from (`told`, or the trip it was learned from). `profile.topics` lists every topic with its kind (`hard_limit` or `taste`), whether it holds several values, and the values it understands.

`POST /api/v1/profile/entries` takes the traveller's own words. They become an entry only when they plainly are one of a topic's values or an allergy; anything else is kept as a note, which is shown and does not yet affect suggestions. `hard` says the traveller means a rule never to be broken; only then is a bare "no shellfish" read as an allergy.

Changes to the profile are not replay-protected: an entry is changed or removed by its id, and saying the same thing twice keeps one entry or one note. Every change raises `profile.revision` and is kept in the profile's history.

A plan stores only these choices. Times, travel, and flags are worked out afresh each time from the choices, the trip's facts and its commitments, so the same choices always give the same plan.

Notes:

- **Creating a trip** is not replay-protected, because there is no trip yet to hold the ledger entry. A client must not send it twice.
- **Tickets** become fixed commitments of kind `TRANSPORT` and set the trip's dates and cities. Each ticket destination is looked up once; one that cannot be matched is left for the traveller to set in the facts.
- **Dates and times** are wall-clock values at the place (`YYYY-MM-DD`, `HH:MM`), with no time zone.
- **Clashes** are reported, never resolved: both commitments are kept (TB-FIX-06).
- **City lookup** must be called when the traveller submits a search, never while typing. The lookup service forbids search-as-you-type ([ADR-009](../architecture/adr-009-place-data-provider.md)).

Reading a trip's facts or the list of trips has no route yet: the website renders both on the server. Add `GET` routes when a client needs them.
