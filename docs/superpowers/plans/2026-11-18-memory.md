# Memory (Milestone 6) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** The site remembers a traveller's taste and hard limits across trips, says where each memory came from, never breaks a hard limit, and lets the traveller see and change everything it believes.

**Architecture:** The Memory service owns a personal profile per traveller: entries on a fixed set of topics, each with a kind (hard limit or taste), a sureness and a source. A trip's profile starts from it and wins where they differ. Rules about which value wins and what may be learned are pure functions; stores keep entries and an append-only history. The conversation reads the profile to confirm instead of ask; the ranking reads hard limits to drop or mark places.

**Tech Stack:** Next.js 16.2 App Router, React 19, Prisma 7 on PostgreSQL (Neon), Zod 4, Vitest, Playwright. No new dependency.

**Spec:** [PRD](../../prd.md) sections 7.6 and 12; [requirements](../../requirements.md) TB-MEM-01 to 14, TB-AGT-06, TB-AGT-12; [roadmap](../../roadmap.md) Milestone 6; [ADR-008](../../architecture/adr-008-modular-services-in-one-deployment.md), [ADR-010](../../architecture/adr-010-service-borders-by-shrinking-exceptions.md). Builds on [Milestone 5](2026-11-19-guided-planning.md).

## Global Constraints

- Service borders: import a service only through `index.ts` or `contracts.ts`; query only tables the service owns; never add to `eslint-suppressions.json`.
- Every change to a trip goes through a route under `/api/v1` with `operationId` and `expectedRevision`, through the replay ledger. A change to the personal profile is not a change to a trip: it carries the profile's own revision.
- **A traveller sees and changes only their own profile.** Every query is scoped by the signed-in user's id; another traveller's entry answers 404.
- **Hard limits are never broken** (TB-MEM-05). A place whose data conflicts with one is not proposed. A place whose data cannot confirm it is marked unconfirmed. No sentence says a place is safe for an allergy.
- **A stated preference is never overwritten by a learned one** (TB-MEM-10).
- **The trip profile wins** over the personal profile where they differ (TB-MEM-02).
- The AI model never writes the profile. Anything it reads from a message is confirmed by the traveller with one tap before it is saved (TB-MEM-07, TB-TRU-03).
- Everything works with the AI model off. Tests and QA run with `AI_MODE=off` and `PLACE_PROVIDER_MODE=mock`.
- Migrations are written with `prisma migrate diff` and applied with `prisma migrate deploy` to the development database only. An applied migration is never edited. No table is dropped in this milestone.

## Decisions made by the builder

Not stated in the PRD. Each is open to change.

1. **Topics** are the eight taste topics of Milestone 5 plus two for hard limits: `dietary_rules` and `allergies`. Budget range is kept as the `budget` topic. A statement that fits none is a **note**: saved, shown on the profile page as "noted, not yet affecting suggestions", and used by nothing (TB-MEM-14).
2. **Kind.** `dietary_rules` and `allergies` are hard limits. Everything else is a taste. The traveller cannot turn a taste into a hard limit in this milestone.
3. **Sureness** has three steps, shown in plain words: "I think" (learned from one pattern), "usually" (learned and seen again), "always" (the traveller said so). A stated entry is always "always".
4. **Source** is "you told me", or the trip it was learned from. An entry learned from several trips names the most recent.
5. **The food question changes.** Milestone 5 asked one food question with dietary choices. It becomes two: dietary rules (a hard limit) and food likes (a taste). Existing trip answers on `food` are read as dietary rules.
6. **Confirming instead of asking** (TB-AGT-06). Where the personal profile holds an answer, the question becomes "Last time you liked a relaxed pace (from your Tokyo trip). Same again?" with "Yes" and "Different this time". "Yes" copies the value to the trip profile.
7. **Why this trip differs** (TB-AGT-12). When an answer conflicts with a personal entry, the agent asks once: "That is different from your usual. Is this trip different?" with the purposes as choices and a skip. The answer is saved on the trip as its reason, and the trip is marked as different. Behaviour in such a trip teaches nothing (TB-MEM-09).
8. **General statements with the model off** (TB-MEM-07). After a dietary rule or an allergy is given in a trip, the agent asks "Should I remember that for every trip?" with one tap. With the model on, a typed "I'm vegetarian" gets the same question.
9. **Learning** (TB-MEM-08) runs when a plan is marked finished. It looks at what was told in that trip and at which kinds of place were picked and turned down. A taste reaches the personal profile when the same value shows in two or more finished, ordinary trips. It never touches a stated entry or a hard limit.
10. **Forgetting** (TB-MEM-12). Deleting a learned entry records which trips it came from. Those trips are not counted for that topic again.
11. **History** (TB-MEM-13). Every change to the personal profile or a trip profile appends a row with the entry before and after, who caused it (the traveller, or learning from a named trip) and when. There is no undo screen in this milestone; the history is the record.
12. **Dietary data** (TB-MEM-05). OpenStreetMap's `diet:*` tags are saved with each place: `yes` and `only` confirm, `no` conflicts, anything else is unknown. Allergies can never be confirmed from place data, so every meal card for a traveller with an allergy says to check with the venue.
13. **The earlier preference tables** (`UserTravelPreference`, `TripPreference`, `PreferenceProfileVersion`) are left alone. Removing them waits for the developer, with piece 7b of Milestone 4.

## Review Focus

1. Traveller A can never read, change or learn from traveller B's profile or trips, on any route.
2. A learned taste never replaces a stated one, and never appears after one trip.
3. A deleted learned entry does not come back when another trip is finished, unless a new trip adds new evidence.
4. With a dietary rule set, no card is shown for a place tagged as not serving it, and an untagged place says it could not be confirmed.
5. A trip marked as different changes the personal profile only through a statement the traveller confirmed.

## Pieces

Each piece gets its task list in its pull request. What is fixed here is what each one produces.

### Piece 1: Profile rules (pure)

**Produced (pull request 34), in `src/features/memory/`:**

- `contracts.ts`: the profile's topics (`PROFILE_TOPICS`: the eight taste topics, `budget`, and the two hard limits `dietary_rules` and `allergies`), `ProfileEntry` (one value on a topic, its sureness and its source), `ProfileNote`, `kindOf`, and the plain words for sureness and source. An entry is one value: "museums" and "views" are two entries on interests, each with its own source.
- `profile-rules.ts`: `tasteInUse(personal, trip)` (said for this trip, then remembered, then the default of a skipped question); `limitsInUse(personal, tripRules)` (a trip adds hard limits and never removes one); `conflicts(values, remembered)`; `learnedEntries(stated, evidence, forgotten)`, the whole set finished trips have taught, so the store only has to replace the learned entries with it.

Nothing uses these yet; pieces 2 to 7 do.

### Piece 2: Profile store and history

**Produces:** tables `profile_entries`, `profile_history` and `forgotten_evidence` (Memory), and history for trip profiles; `readProfile`, `saveEntry`, `deleteEntry`, `resetProfile`, all scoped by user id; tests that one traveller cannot reach another's rows.

### Piece 3: Profile routes and page

**Produces:** `/api/v1/profile` (read, add, edit, delete, reset); the Profile page rebuilt on real data to the approved prototype: entries grouped by topic with source and sureness, notes shown as not yet affecting suggestions.

### Piece 4: The conversation uses the profile

**Produces:** a trip profile that starts from the personal one; confirm-instead-of-ask questions naming the trip a memory came from; the "why is this trip different" question, its answer on the trip, and the trip marked as different.

### Piece 5: General statements

**Produces:** the one-tap "remember that for every trip?" question after a dietary rule or allergy, and after a typed general statement when the model is on.

### Piece 6: Hard limits in proposals

**Produces:** dietary tags saved with places (an additive column); the ranking drops a place that conflicts with a hard limit and marks one that cannot be confirmed; the card and its reason say so.

### Piece 7: Learning from finished trips

**Produces:** learning when a plan is marked finished; the two-trip rule; no learning from a trip marked as different; no relearning of deleted evidence.
